# Инструкция: от установки до работы

Документ покрывает два сценария: **(A)** запуск тестовой лабы на своём компе (для демонстрации)
и **(B)** развёртывание на реальных серверах Ubuntu. Код один и тот же — отличаются только
адреса/креды в конфигах.

---

## 0. Требования

- **Docker** и **Docker Compose v2** (Docker Desktop на Windows/Mac или `docker-ce` на Linux).
- Доступ в интернет у нод-агентов (NSE-скрипт `vulners` тянет базу CVE онлайн).
- Для реального деплоя — серверы Ubuntu 22.04/24.04 с root/sudo.

Проверить Docker:
```bash
docker --version
docker compose version
```

## A. Тестовая лаба на своём компе

### A1. Поднять
```bash
git clone <repo> pintest && cd pintest
bash lab/build.sh
```
Первый запуск ~5–8 минут (собирается `amneziawg-go` из исходников). Дальше — секунды.

### A2. Открыть вебку
- Браузер → **https://localhost:8443**
- Самоподписанный сертификат — «Дополнительно → Перейти на сайт».
- Логин **admin / admin**.

### A3. Работа — по шагам
Полный сценарий с указанием, что скринить, — в [../lab/README.md](../lab/README.md). Кратко:
1. **Агенты** → добавить `agent1/2/3` (host = `agent1`…, user `root`, пароль `pintest`).
2. **Цели** → вставить `lab/dirty-targets.sample.txt` → «Сохранить и почистить».
3. **Скан** → выбрать параметры → «Запустить».
4. **Отчёты** → смотреть/скачивать отчёт.
5. **Эксплуатация** → назначить ноде роль exploiter → check → (подтвердить) закрепиться.

### A4. Управление
```bash
docker compose -f lab/docker-compose.yml ps
docker compose -f lab/docker-compose.yml logs -f backend
docker compose -f lab/docker-compose.yml down            # стоп, данные сохранятся в lab/data
docker compose -f lab/docker-compose.yml down -v; rm -rf lab/data   # снести всё
```

## B. Реальные серверы

### B1. Хостовый сервер (control plane)
```bash
git clone <repo> pintest && cd pintest/host
sudo bash install.sh          # --fresh — чистый старт (снести host/data)
```
`install.sh` (цветной пошаговый вывод, шумный apt/docker — в `/tmp/pintest-setup.log`): ставит
Docker, **хардненинг** (ufw + fail2ban `backend=systemd` + sysctl), PostgreSQL **17**, создаёт/мягко
дополняет `host/.env`, поднимает стек. **Спросит SSH-порт**: Enter — оставить текущий (с
rate-limit), другой — безопасно перенесёт sshd (маскирует `ssh.socket`, ufw включит только после
подтверждения порта — без лок-аута). Адрес хоста (`AWG_ENDPOINT`) **определяется сам** — вручную
только при сложном NAT. Свои креды/порт задай ДО первого старта в `.env`:
```
ADMIN_PASSWORD=<свой пароль>
# AWG_ENDPOINT=203.0.113.7:51820   # только если авто-детект ошибётся
# AWG_NO_EXTERNAL=1                 # закрытый лаб без интернета (брать IP интерфейса)
```
и перезапусти: `docker compose up -d`.

Вебка: `https://<host>` (чистый IP, без порта; http→https). **Доступ желательно только из VPN-подсети** (в `ufw` сузь правило
для 80/443). Порт `51820/udp` должен быть открыт наружу — это вход туннеля.

### B2. Агент-нода (на каждом удалённом сервере)
На ноде вручную **ничего ставить не нужно** и репозиторий клонировать **нельзя** (это деанон).
Нужен только доступный **SSH** (root + пароль или ключ). Docker/код/туннель — всё развернёт
**хост** при подключении из вебки (см. B3), скопировав исходники с себя.

### B3. Подключить ноды из вебки
На хосте открой вебку → **Агенты** → «Добавить ноду»: имя, SSH host/порт/user/пароль ноды,
галка **«полная установка с хоста (без git)»** → **Подключить**. Хост по SSH: `apt update/upgrade`,
поставит Docker, **скопирует код с себя тарболом** (не git clone), соберёт и поднимет контейнер-агента,
вбросит VPN-ключ, поднимет туннель и взведёт self-destruct. Сними галку, только если агент уже стоит
и нужно просто переподнять туннель. Повтори для каждой ноды.

## Механики, о которых стоит знать

### Подключение ноды: SSH + автонастройка (креды с вебки)
Ты вводишь в вебке только SSH-креды ноды — дальше хост настраивает её сам:
1. В UI «Агенты» → «Добавить ноду»: имя, SSH host/порт/user/пароль.
2. Хост генерирует ключевую пару AmneziaWG для ноды и выделяет ей туннельный IP (`10.9.0.X`).
3. Хост **заходит на ноду по SSH** (с этими кредами, библиотека paramiko) и **вбрасывает
   клиентский VPN-конфиг** (`/etc/amnezia/amneziawg/awg0.conf`).
4. На ноде запускается `apply-awg.sh` → поднимается туннель (`awg-quick up awg0`) → нода
   дозванивается к хосту (инвертированный туннель).
5. Хост добавляет пир на сервере и проверяет доступность API ноды по туннелю (`/health`).
6. Нода появляется в топологии зелёной. **На ноде вручную не делаешь ничего** — при «полной
   установке» хост сам ставит и разворачивает агента из скопированного кода (репа не клонируется).

Полный деплой: [`provisioner.deploy`](../host/backend/app/provisioner.py) (тарбол исходников + `deploy.sh`
на ноде: apt → Docker → **хардненинг ноды (fail2ban под её SSH-порт, от root — ufw на docker-хосте не включаем)** → сборка из копии
→ контейнер → туннель → dead-man). Ре-провижн (только туннель):
[`provisioner.provision`](../host/backend/app/provisioner.py) → [`apply-awg.sh`](../agent/scripts/apply-awg.sh).

**Хардненинг ноды:** `deploy.sh` на агент-сервере ставит fail2ban (journald + ignoreip приватных
сетей) от родного root. **ufw на ноде НЕ включаем**: агент-сервер — docker-хост, а `ufw enable`
ставит FORWARD-policy DROP и рвёт сеть контейнера-агента (нода не дозвонится по туннелю → LOST).
Отключить хардненинг: `AGENT_HARDEN=0`. SSH-порт ноды виден на **топологии** (подпись агента:
`<tunnel_ip> · SSH:<порт> · статус`), а в форме «Добавить ноду» поле «Порт» **автозаполняется**
SSH-портом хоста и запоминает последний введённый (чтобы не ловить LOST из-за порта).

### Самоуничтожение ноды (dead-man switch)
Нода спроектирована самоуничтожаемой:
- «Выключатель мертвеца» ([`deadman.py`](../agent/agent_api/deadman.py)) взводится **идемпотентно**
  самим агентом (не `apply-awg.sh`): нода вооружается только после установки И устойчивой связи с хостом
  (`DEADMAN_ARM_GRACE`=15с непрерывной reachability). Reachability = ping ИЛИ свежий handshake.
- Если ВООРУЖЁННАЯ нода теряет связь с хостом дольше `DEADMAN_TIMEOUT` (90с — заметно больше
  keepalive 25с, чтобы джиттер не давал ложняк) — обрыв интернета,
  падение туннеля, изоляция — запускается [`self-destruct.sh`](../agent/scripts/self-destruct.sh):
  туннель вниз, стираются ключи/конфиги/результаты/код проекта, нода гаснет. Всё в пределах
  проектной папки — безопасно для остальной системы.
- Есть и **ручной триггер** — кнопка «уничтожить» в UI (эндпоинт `/destroy`).
- Поднять ноду заново после самоуничтожения — тем же provisioning из вебки (или пересобрать образ).

### Роли и эксплуатация (CTF)
- Нода по умолчанию — **scanner**. Роль **exploiter** назначается вручную выбранным нодам
  (вкладка «Агенты»), при этом на ноде идёт **донастройка** (доустановка модулей).
- Эксплуатация — две фазы: **check** (безопасная проверка, заведётся ли CVE) и **capture**
  (закрепление). **Capture выполняется только после явного подтверждения** галочкой в UI.
- Только авторизованный лаб/CTF-скоуп.

### Автоэксплуатация (real-time) и self-spreading
Движок превращает находки скана в атаку сам, без файла-эксплойта на каждую CVE (покрытие —
строки каталога `exploits/catalog_data.py`).
- **Авто по цели.** Определилась CVE по хосту → движок собирает «модуль на лету» → `check` →
  (с подтверждением/авто-режимом) `capture`. Разведка — без подтверждения (что реально берётся),
  захват — с ролью exploiter и явным согласием.
- **Self-spreading (pivot-авто).** Захваченный узел сам сканит скрытую подсеть и авто-захватывает
  найденное **своим трафиком** — граф разрастается сам. Ради этого всё и затевалось на CTF-полигоне.
- **Расширение покрытия — строкой каталога**, а не новым файлом: добавил веб-RCE delivery-спеку
  или дефолт-креды сервиса — движок уже умеет. Подробно: [`exploitation.md`](exploitation.md).

### Действия прямо на графе (клик по узлу)
Вкладка «Обзор» → **клик/тап по узлу** цели → меню: **🎯 Авто-эксплойт**, **🛰 Pivot-авто**
(через захваченный/двудомный узел), **🖥 Консоль**. Быстрее, чем ходить по вкладкам.

### Отказоустойчивость
- Хост опрашивает ноды (heartbeat). Если нода выпала — её чанки перераспределяются на живые,
  отчёт продолжается (не собирается заново).

### Самоуничтожение
- Нода, потерявшая связь с хостом дольше таймаута, полностью стирает проект у себя
  (взводится только после успешного provision). Есть и ручная кнопка «уничтожить».

### Данные и бэкапы
- Всё ценное (БД, отчёты, ключи агентов, **ключи VPN-сервера** `data/vpn`, серты) — на диске через
  volume `./data` у хоста, переживает пересоздание контейнеров.
- **Бэкапы** (вкладка «Бэкапы»): снимок durable-состояния = дамп всех таблиц БД + отчёты + ключи
  агентов + идентичность VPN-сервера + серты. Каждый архив: `meta.json` (версия/причина/дата) +
  `sha256`. Причины: `manual|cron|update|pre-restore`. Снимок делается **автоматически** перед
  обновлением и восстановлением, плюс ежедневно 03:30; ротация `BACKUP_KEEP` (10). Кнопки:
  создать / скачать / **загрузить** (перенос на новый хост) / удалить / восстановить. Restore
  проверяет sha256, снимает pre-restore страховку, льёт файлы поверх + перезаливает БД + просит
  vpn-контейнер перечитать awg0.

### Обновления (две разные механики)
- **Хост** обновляет себя сам. Бэкенд в контейнере не может пересобрать себя, поэтому кнопка
  «Обновить хост» пишет маркер `host/data/.update-request`, а на хосте крутится демон
  `sudo bash host/update.sh --watch` — ловит маркер и делает `git fetch` + `git reset --hard` +
  `docker compose up -d --build` с **авто-откатом** при ошибке. Разово: `sudo bash host/update.sh`.
  Перед обновлением автоматически снимается бэкап (`reason=update`).
- **Агенты** обновляются доставкой С хоста: бандл по API-туннелю (кнопка «обновить») или по SSH.

### Живой граф сети (построение, достижимость, самовосстановление)
Вкладка «Обзор» → топология — это **живой граф**: HOST → агенты → цели. Узлы — чёткие SVG-иконки
(host=сервер, агент=CPU, цель=галочка/alert/crosshair/флаг), у каждого состояния свой цвет/анимация.
- **Построение в реальном времени.** Во время скана цели проходят стадии с анимацией:
  `очередь → пинг (синяя волна) → живой/скан (бирюзовое вращение) → статус`. Сетка «прорастает» по
  мере пинга и сканирования — видно, как хосты оживают и колеризуются.
- **Рокировка:** агент, нашедший цель, выпал → маршрут авто-переносится на другого онлайн-агента
  (синяя связь + ↻) — «агентный узел меняется в реальном времени».
- **Самовосстановление (реле):** если у подсети не осталось живого агента, но там есть **захваченный
  узел** — он становится **реле** (бирюзовый ⇄), и цели за ним остаются доступны. Сеть не теряется.
- **Точки отказа:** панель «Достижимость и точки отказа» показывает, потеря какого агента реально
  отрежет цели (уже с учётом реле — поэтому их немного).
- Граф **масштабируется** на много устройств/сетей: колесо — масштаб, тяни — двигать, 2×клик —
  вписать; подписи разводятся автоматически, зум показывает больше.
- **С телефона:** пан одним пальцем, пинч-зум двумя, **тап по узлу** открывает меню действий.

### Консоль узлов и захваченных целей
Вкладка «Консоль» → выбери узел в списке:
- **Агент** (🖥) — полноценный **bash** по PTY через туннель (стрелки, история, Tab, Ctrl-C).
- **Захваченная цель** (🎯) — командная консоль через её **foothold** (бэкдор/RCE): вводишь команды,
  они выполняются на взятом хосте (`id`, `ls /`, `cat`…). Не PTY (окружение/`cd` не сохраняются),
  но достаточно для управления. Можно несколько вкладок; трафик — `браузер → хост → агент → цель`.

### Вебка с телефона
Панель адаптирована под мобильный: вкладки — свайпаемой полосой сверху, карточки/формы в одну
колонку, граф тянется/зумится пальцами, меню действий по тапу. Доступ — как обычно, **по VPN**:
поставь AmneziaWG на телефон, импортируй админский `.conf` (bootstrap или из вкладки «VPN»),
подключись и открой адрес вебки.

### Админский VPN-доступ (вкладка «VPN»)
Слева — статус сервера AmneziaWG (интерфейс, порт, пиры/handshake). Справа — **админ-конфиги**:
впиши имя → «Создать конфиг» → скачается персональный `.conf` (импортируй в клиент AmneziaWG).
Так админ заходит на вебку по VPN, а не напрямую. Конфиги можно скачивать повторно и удалять.

**Первый вход (bootstrap).** На чистой установке хоста бэкенд на старте сам генерит первый админский конфиг в `host/data/bootstrap-admin.conf` — импортируй его в клиент AmneziaWG и зайди на вебку по туннелю (иначе к панели не подключиться). Дальше конфиги создаёшь тут же, во вкладке.

### Лут (что залутано) и лут-отчёт
Вкладка «Эксплуатация» → «Захваты и лут»: карточки успешных закреплений с **реальным содержимым**
(shell/RCE-вывод: `id/hostname/uname`, снятый флаг, маркер, лог операции). Кнопки — выгрузка
лут-отчёта отдельно: **HTML** (тёмный), **.md**, **.json**.

### Pivot — разведка скрытой сети через захваченный узел
Если захваченная цель **двудомная** (сидит и в сети, которую агенты не видят), можно пробросить
разведку через неё. Вкладка «Эксплуатация» → «Захваты и лут» → у захваченного узла кнопка
**«🛰 развед-скан сети за узлом (pivot)»** → укажи скрытую подсеть (в лабе `10.66.0`). Скан
реально запускается **на плацдарме** (через его foothold), трафик идёт через него; найденные
скрытые хосты появляются в графе **за реле-узлом** (метка `H`, «скрыт»), достижимые только через
захват. В лабе за `172.30.0.11` (vsftpd) спрятана сеть `10.66.0.0/24`, которую агенты не видят.
Дальше кнопка **«🎯 захватить скрытые через pivot»** реально эксплуатирует скрытые веб-цели
(apache 2.4.49) **через плацдарм** — успешно взятые становятся «обработаны» (фиолетовыми) в графе.

**Self-spreading одним действием:** `pivot-авто` (кнопка у узла или в меню графа) сам прогоняет скан скрытой сети + авто-захват всех найденных подходящих целей через плацдарм — проверено на лабе (через vsftpd взяты hidden-apache и скрытый ftp с флагами).

### Отчёты
Вкладка «Отчёты»: отчёт рендерится **нативно в тёмной теме** (сводка + severity-разбивка +
находки по хостам), а не в белом окне. Выгрузка во всех форматах сохранена: **HTML ↗ / .md /
.csv / .json**.

### Полигон устройств (для ручной репетиции)
Отдельный **автономный** скрипт [`../lab/polygon.sh`](../lab/polygon.sh) (только docker CLI, от
проекта не зависит) поднимает заданное число разнотипных устройств — часть в сети целей (агенты
видят), часть изолированно:
```bash
bash lab/polygon.sh up 30     # 30 устройств (web/СУБД/камера/принтер/роутер/telnet/SCADA/VoIP)
bash lab/polygon.sh ips       # IP связанных — вставить в «Цели»
bash lab/polygon.sh down      # снести
```
Число/типы/долю изолированных правь вверху скрипта. Порты не из топ-100 (9100/502/5060/6379)
ищи сканом «все» или списком.

## Диагностика

| Симптом | Что смотреть |
|---------|--------------|
| Вебка не открывается | `docker compose -f lab/docker-compose.yml logs frontend` · сертификат приняли? |
| Нода не подключается | логи provisioning в UI · SSH-креды/доступность ноды · `logs -f backend` |
| Туннель не встаёт | `docker exec -it lab-vpn-1 awg show` · совпадают ли AWG-параметры |
| Нет CVE в отчёте | есть ли у агентов интернет (для `vulners`) · открылись ли порты целей |
| Нода сама пропала | сработал dead-man (потеря связи) — это ожидаемо; подключи заново |

Логи конкретного сервиса:
```bash
docker compose -f lab/docker-compose.yml logs -f backend      # оркестратор
docker exec -it lab-vpn-1 awg show                            # статус туннеля
docker compose -f lab/docker-compose.yml logs agent1          # агент
```
